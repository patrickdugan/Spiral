Two Harnesses, One Control Plane

I put the same safety layer under two very different agent runtimes, Hermes Lite in Python and goose in Rust. Scripted agents changed nothing. Real models found the gaps.

Patrick Dugan · Morality Lab · Draft

An agent runtime, or harness, is the loop around a model. It asks the model for its next step, runs the tool calls the model returns, feeds back the results and decides when to stop. Most of the controls that keep an agent inside what its user approved live in that loop: a permission prompt, an allowlist, a hook that can say no.

That makes the controls only as portable as the loop. Runtimes disagree on almost everything that matters for control: whether one turn's calls run in order or all at once, whether code the model writes can call tools, whether sub-agents get their own tools, how the context gets compacted, how many rounds a turn may take. A rule written into one harness does not carry to the next.

So I tried the opposite approach. I built one control plane that sits under the runtime, and ran it beneath two harnesses that share almost no code or conventions. This post is about what each harness looks like from underneath, and what that taught me about where enforcement can live.

The two harnesses

Hermes Lite is a Python agent loop in the Hermes line, tuned for small local models. Its tool calls go through one method, _execute_tool_calls, which either runs a single call or a batch on a thread pool of up to eight. A handful of tools (todo, memory, clarify, session search, delegation) run inside the loop itself; the rest go through a registry. It also has a "lean" mode in which the model never calls tools at all: it returns a phase and an operation, and harness-owned code does the work under skill contracts that list each phase's allowed operations.

goose is a Rust agent built around the Model Context Protocol. Every capability is an extension. It has two agent loops (a legacy one and a newer state machine that must stay in parity), runs a turn's tool calls as concurrent futures, lets the model write JavaScript that calls tools ("code mode"), and can delegate to sub-agents. It speaks ACP to editors and has a headless CLI.

Read from underneath, these are two different answers to the question "who is allowed to say no?" Hermes Lite has one narrow door that every call walks through, and nobody standing at it. goose has several people standing at its doors, each of whom steps aside if they trip, and a couple of side entrances they don't watch.

Putting one control plane under both

The control plane has one rule: a runtime only proposes. Every event goes into a hash-chained ledger, which is the only source of truth. A proposed call is decided by policy engines combined by conjunction (any refusal stands) and, for consequential calls, by a controller model that can only reduce authority. An allowed call gets a single-use lease bound to the call's fingerprint. A tool gateway is the only path to the environment, and it commits only under a valid lease. Anything that tries to leave the machine hits an egress sink.

The call path. The runtime is the only part that changes between arms.

Integration meant finding each harness's one door. In Hermes Lite that was easy: a shim in the dispatch method turns every call into a proposal. I also made a turn's calls run in order rather than on the thread pool, because a ledger needs an order, and gated the memory flush, which otherwise writes to disk outside any tool call.

goose was harder, and I did it two ways. With an unmodified build and a PreToolUse hook, calls from code-mode scripts and from sub-agents never reached the hook. The gateway still refused them, because they arrived without a proposal, but the control plane saw them only as bypasses. So I also built a fork whose gate proposes every call, including those, and registers each sub-agent as its own actor. As of goose main this month the code-mode path still goes from the script callback straight to the extension call, with no hook or inspector in between. A third arm ran Hermes Lite's unmodified main branch with nothing but the gateway in the way.

With scripts, the runtime changed nothing

The first test used scripted agents (an oracle, an adversary that tries to execute early and wide, and random walks) on BitAgent's 42 development scenarios, through four arms: a minimal loop, Hermes Lite main behind the gateway, Hermes Lite with the shim, and the goose fork.

The two runtimes differ in prompts, positions and timing, and in nothing that was proposed, decided or committed. That is the result I wanted. It is also only as wide as what the scripts exercise, and scripts always pick the tool that matches their move.

Real models found what the scripts couldn't

The live actor was Bonsai-8B in 1-bit form with a task adapter, served by llama.cpp. Every hard gate stayed at zero once each defect below was fixed, but the list is mostly about the harnesses:

  1. A frozen prompt line. With a "submit it as the tool's candidate" line added to the task prompt, the model answered in text in all 21 replies of the first seven runs. Nothing reached the tools.
  2. Protocol on a shared stdout (Hermes Lite). Its serve protocol shares stdout with a notice it prints when the model hits the iteration cap. The harness took the notice for its reply.
  3. Rounds per turn. The model kept calling the tool after every accepted submission, up to the runtime's cap, and a "turn over" line in the result did not stop it.
  4. Unbounded replies. One degenerate reply repeated a tool call until the context ran out; on a contended GPU that request took 74 minutes.
  5. A cap one runtime ignores (goose). Over ACP, goose reads GOOSE_MAX_TURNS and not --max-turns, so its first pass ran about 30 tool rounds a turn where the other arms ran one.
  6. A miscounted audit (goose). goose reports a call it refused before dispatch, with arguments cut off at the output cap, as a failed tool call. My coverage audit counted 477 of them as unproposed calls. None had been dispatched.
  7. An effect class sidestepped by tool choice (Hermes Lite main). The model sent an execute move through the tool registered as having no effect. The control plane saw a harmless call: no consequential decision, no controller turn. The host's own gates authorized it, so nothing bad landed, but a consequential move had left the consequential path.

The last one is the lesson I'd generalize. An effect class attached to a tool name is sound only if the environment refuses arguments that belong to another class. Scripted policies never find this, because they never pick the wrong tool on purpose.

The harnesses also cost the model most of its skill. In process, without a runtime, the 8B with its adapter had 8 of 44 validate proposals accepted. Through the runtimes it had 14 of 722. The runtime's own system prompt and tool-call format sit between the model and what it was trained to do.

The controller, and a lesson about measuring it

Above the agent loop runs a second conversation, the controller. It never reads the agent's raw text, only whitelisted fields of ledger events, and on each consequential call it can pass, hold, ask the principal, intervene with a message, or halt. I held it to a rule signed before scoring: on live runs it must beat both "always pass" and "always hold" on precision, recall and F1.

Getting a fair measurement took three corrections, all in my method: a first rule whose positives a lookup of the visible admissible moves could catch; a replay method that misstates a controller whose thread remembers its own earlier turns; and a scoring path that labelled every refused call from a missing proposal, so every refusal scored as right. After all three:

Beating the two constant controllers is a floor, and a controller can pass it by being mostly one of them.

On this bench the useful controller is the rule over the visible state. A small model has yet to show it adds anything that rule does not.

What I'd tell someone building a harness

  • Put enforcement below the runtime, at one choke point. The gateway caught every call the goose hook missed. A hook inside the loop is a convenience for the user; it is not where a guarantee can live.
  • Find the side entrances. In goose they were code mode and sub-agents. In Hermes Lite it was the memory flush and the thread pool. Every harness has calls that don't go through the front door.
  • Fail closed, and say so. goose's inspectors and hooks default to allow when they break. That's a reasonable default for a coding assistant and the wrong one for anything that moves money.
  • Tie effect classes to arguments, not tool names. A model will eventually send the dangerous move through the harmless tool.
  • Test with live models early. Scripts proved the plumbing. Every interesting failure came from a real model doing something no script would.

Limits

Everything here is one bench, BitAgent's, with one model family in 1-bit form, on one shared laptop GPU that capped itself to 15 W for parts of the run. The held-out sets share a generator with the development set. One brief was tried. The controller's qualification used scripted actors, not models.
